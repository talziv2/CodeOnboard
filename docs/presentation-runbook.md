# Presentation runbook

A controlled hybrid demo. **Every session shown is real** — generated by the real
pipeline against the pinned `psf/requests` revision and persisted through the
normal product path. Nothing is static demo data, and nothing in the product
knows a presentation is happening.

What is controlled is *where you start*: generation takes two to three minutes
and succeeds about one run in three (`docs/planning/phases/contribution-journey.md`
§B21), so it is prepared beforehand rather than performed live.

---

## 1. Setup, on the day

Two servers, on their own ports, so nothing collides with an ordinary dev
session on 3000/8000.

```bash
uv run python -m uvicorn scripts.ux_fixture_app:app --port 8124
```

with `CODEONBOARD_UX_DB=data/demo.db` in the environment — that is the only
thing pointing the app at the demo database. Then:

```bash
cd frontend && API_ORIGIN=http://localhost:8124 NEXT_DIST_DIR=.next-demo npm run dev -- --port 3124
```

`NEXT_DIST_DIR` is not optional: a dev server sharing a build directory with
anything else corrupts its own chunks mid-session, which happened twice while
this was being prepared.

Open **http://localhost:3124** and sign in once as `rehearsal@example.test`.
Real authentication, real cookie — there is no demo bypass.

### The Claude Code working copy

`Continue in Claude Code` opens a **writable clone at
`workspace/<owner>/<name>`**, inside this project and gitignored. It is not
`data/repos/<owner>/<name>`: that is the ONE shared, pinned checkout every
anchor in every session resolves against, and an agent editing it would move the
ground under the whole product.

Prepare it once per machine — it clones at the same commit the session's anchors
were resolved against, and writes the `.mcp.json` for that session:

```bash
uv run python tools/prepare_workspace.py --session 73a2248c3d2f4923820c511695ce55fa --db data/demo.db
```

Then the one approval Claude itself requires, also once:

```bash
cd workspace/psf/requests && claude
```

Accept the trust prompt and approve the `codeonboard` server; `/mcp` should then
list it with two tools. After that the button is one click with no prompts.

**Nothing here is machine-specific.** The path is derived from the project root
and the session's repository URL, so another machine reproduces the demo by
cloning CodeOnboard and running the same two commands.

## 3. The run of the demo

Roughly twelve minutes. **Open a working copy of `02` before you start** — see §5.

### Beat 1 — the same repository, two goals *(pre-generated)*

Open `A · Architecture journey`. Show the route: **8 chapters, 19 stops**. Do not
walk it; you are establishing what a broad journey looks like.

> "Same repository. This is what CodeOnboard plans when you say *understand the
> architecture*."

### Beat 2 — the concrete task *(pre-generated)*

Open **`01 · Contribution scope`** and go to the briefing page. The scope card:

- the task, as the developer typed it;
- **"You need 11 concepts before implementing this safely"** — derived from the
  required set, not written anywhere;
- the 11 concepts by name;
- **Not required for this contribution**: `adapters.py`, `auth.py`, `models.py` —
  computed by subtracting what the curriculum anchored on from what the survey
  found, so it is checkable rather than asserted.

> "Same repository, a concrete task. **14 required concepts became 11; 19 stops
> became 12; 8 chapters became 5.** No cap did that — the required set is just
> smaller."

### Beat 3 — one learning stop *(LIVE)*

Open **your working copy of `02`**. It sits on stop 8, *Handle cookies with
value=None* — the non-obvious finding, and the best single argument for the
product: `_find_no_duplicates` treats a `None`-valued cookie as absent, so `get()`
cannot see it while `get_dict()` can.

Click the **Understanding** tab. The question is the critique form: a proposed
`get_all()` containing `if cookie.value:` — truthiness, which silently drops
exactly the case the stop is about.

Answer it live. Say the flaw in your own words and submit. **~2 seconds** through
the Grader; if the question offers options instead, clicking one is ~0.25s and
cannot be flaky.

> "It found an edge case in someone else's library that a careful reader misses —
> and then it checked whether I'd spotted it."

### Beat 4 — readiness *(pre-generated)*

Open **`03 · Ready to implement`**. The gate: *"You've demonstrated all 11
concepts this change depends on."*

Worth saying: this is **derived**, not a button. A learner who clicks *mark
understood* does not open it — a decision is never evidence.

### Beat 5 — the implementation stage *(mixed)*

Watch the **left rail** as you cross the boundary. The implementation stages sit
under the learning route as a second, accented section — subdued and counting
("4 of 11 concepts demonstrated") while the learner is still learning, live once
the gate opens. It is the clearest single image of the claim: **implementation is
the last phase of one journey, not a separate product.** The route stays live
throughout — clicking any stop still opens its lesson, and **Back to
implementation** appears top-right to return.

From `03`, press **Start implementing** — the Plan is written live (~9s) and is
worth watching: it names the target file and line region, the repository's
docstring conventions, the boundary's edge cases, the exact test to imitate, and
the four symbols that must not change. **It writes no code.**

Then step through **Locate** (the change boundary, each row opening the real
source) and **Implement**.

To save typing, open **`04 · Implementation, patch written`**, which already has
the patch. Press **Save and check**.

### Beat 6 — what can and cannot be claimed *(LIVE, deterministic)*

Validate runs in **0.34 s**, no model call:

```
Path scope               Passed — no files outside the planned contribution boundary
Syntax                   All 2 files parse as Python
Symbol                   RequestsCookieJar is defined
Test file                Included — tests/test_requests.py
Protected-symbol check   Not performed — 4 protected symbols; this check
                         compares file paths, not symbols
Repository tests         Not executed by CodeOnboard
```

This is the slide to linger on. Three different claims, kept apart: what our code
checked, what it *could not* check, and what nobody ran.

**If you want to show a failure**, add a file outside the boundary in Implement
and re-check — the scope row names it. Then remove it. The check can genuinely
fail; that is why it means anything.

### Beat 7 — the result *(pre-generated)*

Open **`06 · PR-ready`**: files changed, scope result, *Repository tests — Not
executed by CodeOnboard*, and a copyable PR title, description and testing notes.
The notes distinguish all three claims, and end **"These tests HAVE NOT BEEN
RUN."**

## 4. Before you present

- **Pre-walk anything you will open.** A stop's first render costs **~12 s**; a
  revisit costs **0.24 s**. Every checkpoint here is already warm — keep it that
  way by not rebuilding one at the last minute.
- **Take a backup**: `uv run python tools/demo_checkpoints.py backup --db data/demo.db --out data/demo-pristine.db`
  (already done — refresh it if you change anything).
- **Do not delete `data/repos/psf/requests`.** The checkout is the pinned
  revision `e8d2c015`, and `clone_repo` never updates an existing checkout, so it
  stays pinned as long as it stays there. Deleting it re-clones at whatever HEAD
  is that day and every anchor in every session goes stale.
- Sign in once and leave the tab open.
- Have `06` open in a second tab as an escape hatch.

## 5. If something goes wrong

**Answer a question badly, or click into the wrong state.** Every checkpoint is
immutable as long as you work on a *copy*. Before the talk:

```bash
uv run python tools/demo_checkpoints.py snapshot --db data/demo.db \
    --session 880773df5762413883af9b1a8cb2d825 --as "LIVE · working copy of 02"
```

That takes about a second, makes no model calls, and prints the new session id.
Present from the copy. If you spoil it, run the same command again and reload —
the checkpoint it came from was never touched.

**One checkpoint is dirty and you want just that one back.** Import it again from
the pristine copy — a re-import replaces the session rather than layering a second
copy over it:

```bash
uv run python tools/demo_checkpoints.py import --from data/demo-pristine.db --session <id> --db data/demo.db
```

**A server dies.** Restart both; nothing is lost. Verified: all eight sessions
survive a full restart of both processes.

**The database gets into a state you do not like.** Restore the whole thing:

```bash
cp data/demo-pristine.db data/demo.db     # then restart the backend
```

**Something is slow.** Skip to the next checkpoint. Every beat has its own
session, so no beat depends on the previous one having worked.

## 6. What is live and what is not

| Live | Pre-generated |
|---|---|
| Answering one learning stop, and its grading | Investigation and planning — 2–3 min, ~1-in-3, and one run took **7129 s** |
| The Plan call, if you want it (~9 s, reliable) | The other 11 stops |
| **Validate** — 0.34 s, deterministic, both outcomes | The patch text (typing it live wastes a minute) |
| Opening source files, moving through the rail | Review and the PR summary, unless you have time |

The audience needs to believe the path was generated *for this task*. The scope
card, the areas and the skipped list carry that. They do not need to watch model
calls happen.

## 7. The one number to have ready

If asked whether the shorter path is just a cap:

> `demoted_by_band` is **0** on every run. Nothing was truncated. The `working`
> band is 8–22 and neither journey came near its ceiling. The contribution
> journey is smaller because its required set is smaller.
